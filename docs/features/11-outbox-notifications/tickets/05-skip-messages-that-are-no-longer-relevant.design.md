| Skipping `AppointmentConfirmed`, `AppointmentRescheduled`, `AppointmentReminder` for bookings no longer `CONFIRMED` (RQ §A7 D-11.7, §B7 Step 2.1, §B9 AC-11.7, TC §B2 TC-11-09) | AC-11.7, D-11.7, TC-11-09 | `api/app/Domain/Notifications/Services/OutboxRelay.php:43-51`, `api/app/Domain/Booking/Repositories/AppointmentRepositoryInterface.php:21`, `api/app/Domain/Booking/AppointmentStatus.php:8`, `api/database/migrations/2026_11_05_000005_create_outbox_messages_table.php:20` | In `OutboxRelay::runOnce`, for claimed messages of types `AppointmentConfirmed`, `AppointmentRescheduled`, `AppointmentReminder`, appointment is resolved via `AppointmentRepositoryInterface::find`. If appointment is missing or status is not `CONFIRMED` (e.g. `CANCELLED`, `COMPLETED`, `NO_SHOW`, `EXPIRED`), `outboxRepository->markSkipped($id, 'NO_LONGER_CONFIRMED', $now)` is executed. The SQL update `UPDATE outbox_messages SET status = 'SKIPPED', last_error = :reason, updated_at = :now WHERE id = :id AND status = 'PENDING'` ensures atomic transition without overwriting concurrent updates. | Applies when appointment was cancelled or deleted prior to relay send. Only claimed rows with `status = 'PENDING'` are updated. | Skipping `AppointmentConfirmed`, `AppointmentRescheduled`, `AppointmentReminder` when booking start time changed (RQ §A7 D-11.7, §B7 Step 2.1, TC §B2 TC-11-11) | D-11.7, TC-11-11 | `api/app/Domain/Notifications/Services/OutboxRelay.php:43-51`, `api/app/Models/Appointment.php:23`, `api/app/Domain/Booking/Services/AppointmentWriter.php:331,411`, `api/database/migrations/2026_11_02_000004_create_appointments_table.php:20` | If the booking is `CONFIRMED`, `payload['start']` is compared against current `$appointment->start_at`. Both are parsed into `CarbonImmutable` instances to guarantee timezone-safe UTC comparison. If `$payloadStart->ne($appointmentStart)`, the message is marked `SKIPPED` with reason `'START_TIME_CHANGED'`. If a booking is rescheduled between outbox message insertion and relay send, stale message is skipped without calling channels. | Only pending claimed rows with start time mismatch are marked `SKIPPED`. Rows for subsequent reschedule events that match current start time remain valid and are sent. | `AppointmentWriter.php:325-335` updating `start_at` on reschedule; `AppointmentQueryService.php` checking slot availability against current times. | follow |
| Exemption of `AppointmentCancelled` and `AppointmentReassigned` events from relevance checks (RQ §A7 D-11.7, §B7 Step 2.1) | D-11.7, INV-11.2 | `api/app/Domain/Notifications/Services/OutboxRelay.php:43-51`, `api/app/Domain/Notifications/OutboxEventType.php:10,12`, `api/app/Domain/Booking/Services/AppointmentTransition.php:96-106` | Events with `event_type` of `AppointmentCancelled` or `AppointmentReassigned` bypass the relevance check. Even though a cancelled appointment has status `CANCELLED` (not `CONFIRMED`), its cancellation notification must be delivered to customer and DMS. Bypassing relevance check ensures cancellation rows proceed directly to recipient resolution and channel dispatch. | Cancellation rows are processed normally even though the underlying appointment entity is in terminal state `CANCELLED`. Inactive bookings receive their terminal notifications. | `AppointmentTransition.php:95` where cancellation explicitly writes outbox notifications; `CustomerChangePolicy.php` handling cancelled states. | follow |
| Relevance check execution order and count tracking (RQ §B7 Step 2, §B9 AC-11.7, TC §B2 TC-11-09) | AC-11.7, D-11.7, TC-11-09 | `api/app/Domain/Notifications/Services/OutboxRelay.php:39-77`, `api/app/Domain/Notifications/Repositories/OutboxMessageRepository.php:105-118`, `api/app/Domain/Notifications/Services/RelayResult.php:9-25` | Relevance check executes as step 2.1 before `RecipientResolver` (step 2.2) and `channel->send` (step 2.3). When relevance check skips a message, `markSkipped` sets `status = 'SKIPPED'` and `last_error` to the skip reason; `$skippedCount` is incremented, and loop advances via `continue` without invoking recipient lookup or channel drivers. Returned `RelayResult` reflects exact skipped tally. | No channel or recipient side effects are triggered for skipped rows. Soft-deleted customer lookups are bypassed since recipient resolution is not called. | `RecipientResolver::resolve` returning null leading to `'NO_RECIPIENT'` skip in `OutboxRelay.php:45-50`. | follow |
| Local per-batch appointment memoization within `runOnce` (RQ §A7 D-11.7, §B7 Step 2) | D-11.7, INV-11.3 | `api/app/Domain/Notifications/Services/OutboxRelay.php`, `api/app/Domain/Booking/Repositories/AppointmentRepository.php:34-45` | During single `runOnce` batch execution, appointment lookups by id are memoized in local array `$appointmentCache`. In a batch of 50 claimed rows with multiple channels (SMS, EMAIL, DMS) for the same appointment, database is queried once per appointment ID instead of up to 3 times, maintaining transactionless lease read semantics. | Inactive or cancelled appointments are fetched once per batch; state is scoped strictly to the method execution and garbage collected on exit. | `AvailabilityService.php` caching opening hours within single slot search; `CandidateFinder.php` caching technician skills. | follow |
