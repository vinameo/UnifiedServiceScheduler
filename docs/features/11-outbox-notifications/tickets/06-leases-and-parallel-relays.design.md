| 60-second lease on claimed rows and retry after lease expiry (RQ §A7 D-11.1, §B3 INV-11.3, §B7 Step 1, TC §B2 TC-11-07) | INV-11.3, TC-11-07 | `api/app/Domain/Notifications/Repositories/OutboxMessageRepository.php:15-50`, `api/database/migrations/2026_11_05_000005_create_outbox_messages_table.php:24,40`, `api/app/Domain/Notifications/Services/OutboxRelay.php:39-40`, `api/tests/Feature/Notifications/OutboxRelayTest.php:465-567` | In `OutboxMessageRepository::claimDue`, `DB::transaction` selects rows matching `status = 'PENDING' AND attempts < 5 AND next_attempt_at <= :now ORDER BY next_attempt_at LIMIT :batch FOR UPDATE SKIP LOCKED`. For selected rows, it atomically executes `UPDATE outbox_messages SET attempts = attempts + 1, next_attempt_at = :leaseExpiresAt, updated_at = :now WHERE id IN (...)` where `:leaseExpiresAt = $now->addSeconds(60)`. When worker process simulates a crash mid-dispatch (e.g. throws `Error` before `markSent` or `scheduleRetry`), the row remains `PENDING` with `attempts = 1` and `next_attempt_at = $t0 + 60s`. Subsequent runs before 60 seconds find 0 due rows. When advancing clock by 61 seconds (`travel(61)->seconds()`), `next_attempt_at <= now` becomes true again, enabling `claimDue` to re-claim the row with `attempts = 2` and deliver it. | Inactive or non-pending rows (`SENT`, `FAILED`, `SKIPPED`) are excluded by `status = 'PENDING'`. Rows with `attempts >= 5` are excluded by `attempts < 5` and handled by `failAbandoned`. Partial index `outbox_messages_pending_idx` speeds lookup. | `ExpireHoldsCommand.php:59-78` checking hold expiry deadlines; `AppointmentTransition.php:57-80` validating status transitions with version checks. | follow |
| Concurrency and mutual exclusion of parallel relay workers via `FOR UPDATE SKIP LOCKED` (RQ §A7 D-11.1, §B3 INV-11.3, §B7 Step 1, TC §B2 TC-11-08) | INV-11.3, TC-11-08 | `api/app/Domain/Notifications/Repositories/OutboxMessageRepository.php:25`, `api/database/migrations/2026_11_05_000005_create_outbox_messages_table.php:30,40`, `api/app/Console/Commands/RelayOutbox.php:16-53`, `api/tests/Support/Concurrency/Parallel.php:18-98` | When 2 CLI worker processes execute `php artisan outbox:relay` simultaneously for 100 `PENDING` rows, each opens a PostgreSQL transaction running `claimDue`. The PostgreSQL lock clause `FOR UPDATE SKIP LOCKED` guarantees that rows acquired by Worker 1's transaction cannot be claimed by Worker 2; Worker 2 skips the locked rows and claims the remaining unreserved rows. Once each transaction commits with updated `next_attempt_at = now + 60s`, neither worker can select the other's batch. Rows are processed and dispatched independently outside transactions, guaranteeing exactly one send per row with 0 duplicates across parallel processes. | Completed rows are updated to `status = 'SENT'` via single atomic updates (`WHERE id = ? AND status = 'PENDING'`). Soft-deleted records and rows already committed as `SENT` by one process cannot be claimed or overwritten by any concurrent process. | `ParallelHoldExpiryTest.php:74-105` testing `holds:expire` racing against customer confirm; `ParallelBookingTest.php:56-100` verifying row exclusion under parallel transactions. | follow |

When `--start-at` is specified in `testing` environment, worker CLI process polls in spin-wait `while (microtime(true) < $targetTime) { usleep(100); }` until the target barrier time before executing `OutboxRelayInterface::runOnce`. This forces both parallel child processes launched via `Tests\Support\Concurrency\Parallel` to enter `claimDue()` and execute PostgreSQL `FOR UPDATE SKIP LOCKED` queries at the exact same microsecond, maximizing concurrency race collision. | No database state is modified during the spin-wait loop. Pre-seeded outbox rows remain unchanged until barrier releases both workers. | `ExpireHoldsCommand.php:40-46` using `--start-at` to synchronize with confirm requests; `TestingRequest.php:67-73` aligning parallel HTTP requests on shared microsecond start. | follow |
