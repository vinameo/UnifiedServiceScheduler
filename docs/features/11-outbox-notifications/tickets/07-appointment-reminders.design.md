| Fresh reminder for rescheduled booking with different start time (RQ §A7 D-11.6, D-11.7, TC §B2 TC-11-11) | D-11.6, D-11.7, TC-11-11 | `api/app/Domain/Notifications/Services/OutboxRelay.php:159-194`, `api/app/Domain/Notifications/Services/ReminderQueue.php`, `api/app/Domain/Booking/Services/BookingService.php:473` | When an appointment with a queued reminder is rescheduled to a new day/time, the old reminder remains in `outbox_messages` with `payload['start']` holding the previous start time. When `OutboxRelay::runOnce` processes the old message, `checkRelevance` compares `$payload['start']` against `$appointment->start_at`; detecting the difference, it marks the stale reminder `SKIPPED` with `last_error = 'START_TIME_CHANGED'`. Later, when the appointment's new `start_at` enters `[now + 23 h, now + 25 h)`, `ReminderQueue::queue` generates `dedupe_key = "reminder:{$appointment->id}:{$newStartIso}"`. Because `{$newStartIso}` differs from the previous start time, the unique constraint does not conflict, inserting a new `PENDING` reminder for the new time. | The previous reminder message is in `SKIPPED` status with the old dedupe key (`reminder:{$appointment->id}:{$oldStartIso}`). The new reminder has a unique new dedupe key. Both coexist without constraint violations. | `OutboxRelay.php:184-191` skipping outdated `AppointmentConfirmed` and `AppointmentRescheduled` messages when start time changed. | follow |
| Service isolation, small transaction, and interface contract (RQ §A7 D-11.6, §B4, §B5, README §6.3) | D-11.6, INV-11.7 | `api/app/Domain/Notifications/Services/ReminderQueueInterface.php`, `api/app/Domain/Notifications/Services/ReminderQueue.php`, `api/app/Providers/DomainServiceProvider.php:124`, `docs/features/README.md:209` | `ReminderQueueInterface` defines `queue(CarbonImmutable $now): int`. `ReminderQueue` implements this interface, querying candidate appointments via `AppointmentRepositoryInterface` and inserting reminder rows via `OutboxMessageRepositoryInterface`. The queueing operation is wrapped in its own small database transaction (`DB::transaction`), keeping it completely isolated from booking changes or HTTP requests. Domain interface is bound to the implementation in `DomainServiceProvider::$bindings`. | Uncommitted transactions or aborted queueing runs rollback cleanly; committed reminders are immediately visible to subsequent relay runs. | `OutboxRelay.php` running outside booking transactions; `ExpireHoldsCommand.php` transitioning expired holds in independent transactions. | follow |
