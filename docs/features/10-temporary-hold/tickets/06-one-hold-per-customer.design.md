| Migration pre-check and partial unique index: pre-check verifies no duplicate HELD rows per customer (`SELECT customer_id, count(*) FROM appointments WHERE status = 'HELD' GROUP BY 1 HAVING count(*) > 1`), aborting with customer ID and remediation if violations exist; `up()` creates partial unique index `appointments_one_hold_per_customer` on `appointments (customer_id) WHERE status = 'HELD'`; `down()` drops index (DB §B1-B2, DB-10.1, TC-10-17) | INV-10.2, DB-10.1 | `api/database/migrations/2026_11_10_000001_add_one_hold_per_customer_index.php`, `api/tests/Feature/Booking/Hold/HoldIndexMigrationTest.php` | Pre-check reads current appointments table; if duplicate HELD holds exist, throws RuntimeException before index creation; otherwise creates partial unique index in PostgreSQL | Pre-check does not delete rows; tells operator to run `holds:expire`; index scopes strictly to `status = 'HELD'` so EXPIRED and CANCELLED rows are ignored | Exclusion constraints and partial unique indexes in `2026_11_05_000001_create_appointments_table.php` and `2026_11_05_000002_create_resource_allocations_table.php` | follow |
| New hold expires older hold in same transaction: when a customer creates a new hold, domain service locks customer row FOR UPDATE, checks for existing HELD appointment after lock acquisition, transitions old hold to EXPIRED (deactivating its allocations and recording EXPIRED event with null outbox), and inserts new HELD appointment within the same database transaction (RQ §A7 D-10.4, §B7 step 4, §B9 AC-10.5, TC-10-05) | AC-10.5, INV-10.2, INV-10.5 | `api/app/Domain/Booking/Services/BookingService.php:212-255`, `api/app/Domain/Booking/Services/AppointmentTransition.php:68-70`, `api/tests/Feature/Booking/Hold/HoldTest.php` | Customer row locked FOR UPDATE serialising hold requests; old hold read after lock and transitioned to status EXPIRED with version incremented; new hold inserted at version 1; both commit atomically | Old hold allocations deactivated via `ResourceAllocationRepository::deactivateFor($id, $now)`; old appointment status marked EXPIRED; no rows deleted | Status transition and allocation deactivation in `AppointmentTransition::transition` and `ExpiredHoldReleaser` | follow |
| Failed new hold keeps old hold intact: if new hold fails due to no availability (409 NO_AVAILABILITY) or concurrent constraint clash (23P01 exhaustion), validation aborts before expiry or enclosing transaction rolls back, leaving old hold HELD with version and allocations completely unchanged (RQ §A7 D-10.4, §B7 step 4, §B9 AC-10.6, TC-10-06) | AC-10.6, D-10.4 | `api/app/Domain/Booking/Services/BookingService.php:183, 215-238`, `api/tests/Feature/Booking/Hold/HoldTest.php` | When candidate finder returns empty pairs, NoAvailability is thrown before write transaction begins; if write transaction encounters failure, DB::transaction rolls back all updates and inserts | No rows modified, deleted, or deactivated; old hold retains active TECHNICIAN and BAY allocations with original version | Atomic rollback on failure in `BookingService::confirmHold` (vehicle clash rollback keeping HELD status) | follow |
